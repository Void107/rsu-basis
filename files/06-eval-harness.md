# 06 — Golden Set 与自检报告

**先建 golden set，再写引擎。** 没有它，迭代就是玄学：改一句解析规则后无法知道是变好还是变坏，而这类产品的错误是静默的。

内部试用阶段有一个额外约束彻底改变了方法论：**你不能收集同事的文档。** 见 §2。

---

## 1. Golden set 的两个合法来源

| 来源 | 数量目标 | 特点 |
|---|---|---|
| **你自己的文档** | 6–8 组 | 跨 3 个税年最好。至少 3 组用纸笔手算过 |
| **合成构造** | 15–20 组 | 用公开股价历史构造，答案由构造过程直接给出 |

内部试用阶段，**合成集是主力**，不是补充。这是被迫的，但结果更好：合成集能精确制造边界条件，而真实文档只能碰运气覆盖到。

必须构造的边界条件：

- vest 后恰好一年卖出（short）与一年零一天（long）
- 闰日 vest：2024-02-29 vest，2025-03-01 卖
- 同日多 grant vest，sell-to-cover 股数无法唯一配对
- 一笔卖出跨多个 lot 且 term 不同
- 分数股（12.3456）
- 单 lot 多次分批卖出
- 全部卖出 / 零卖出
- Adjusted Cost 列是总额而非每股

## 2. 为什么不收集同事的文档

三条独立的理由，任何一条都足够：

**公司数据政策。** W-2 是 HR 数据。你没有正当业务理由持有同事的 W-2 和券商对账单。这大概率直接违反 Zoom 自己的数据处理政策——与税法无关，是纪律问题。

**泄露通知义务。** 一旦你的笔记本上有 30 个同事的 SSN，设备丢失时州级数据泄露通知法照样适用。个人身份不豁免。

**去标识不可靠。** 金额 + 日期 + ticker 的组合在小样本内很可能定位到具体的人。「脱敏后」不等于「不可再识别」。

所以：`test/golden/` 里只放你自己的和合成的。**不设 `golden-private/` 这类目录**——一旦存在，它就会被用来放不该放的东西。

---

## 3. 那怎么覆盖别的券商版式？

同事能给你的**不是数据，是版式信息**。写适配器需要的是表头结构，不是里面的数字。

三种零风险的贡献方式，按有用程度排序：

### 3.1 结构描述表（最有用）

给同事一张表让他填：

```
券商名称：
补充表标题原文：
补充表起始页码：
必需列的列头原文（照抄，不要改写）：
  vest 日期列          → "________"
  每股 FMV 或调整后成本 → "________"
  ordinary income 列    → "________"
  股数列               → "________"
是否有印刷合计行：是 / 否，位置：
调整后成本列是每股还是总额：
特殊之处（跨页、括号负数、多 CUSIP 混排等）：
```

这足以写出适配器的 80%。**里面没有一个数字。**

### 3.2 遮盖后的版式截图

同事自己用图片编辑器把所有数字涂黑，只留表头和布局。发给你之前自己检查一遍。

**你要明确告知**：不要发未遮盖的截图，如果收到了你会立即删除并告知对方。

### 3.3 自检报告（见 §4）

同事本地跑，工具自动产出一份不含数值的诊断报告。

## 4. 自检报告（self-check report）

这是内部试用能拿到覆盖信号的主要机制。同事跑完后，工具生成一份 JSON，他可以自己看一眼再决定发不发。

### 4.1 内容

```json
{
  "reportVersion": 1,
  "appVersion": "0.4.2",
  "brokerDetected": "fidelity",
  "brokerConfidence": 0.97,
  "taxYear": 2025,
  "docPageCount": 62,
  "supplementalFound": true,
  "supplementalStartPage": 47,
  "lotCount": 14,
  "saleCount": 21,
  "checks": [
    { "id": "C1", "status": "fail", "deltaMagnitude": "1e2" },
    { "id": "C2", "status": "pass" }
  ],
  "failurePath": "F11",
  "columnHeadersSeen": ["Date Acquired", "Ordinary Income Reported", "..."],
  "durationMs": 3400
}
```

### 4.2 硬性约束

报告中**绝对不得包含**：

- 任何金额、股数、日期（`taxYear` 除外）
- 姓名、雇主名、ticker、账号
- 文件名、文件哈希
- 原始文本片段

`deltaMagnitude` 只给数量级（`1e2` 表示差额在百位），不给具体值。这足以判断是「差了一行」还是「差了几分钱」。

`columnHeadersSeen` 是例外——列头是券商的公开版式，不是用户数据。但要过一遍白名单：只保留匹配已知模式的表头，不透传任意文本。

### 4.3 实现要求

- 报告生成后**先展示给用户看全文**，再由他手动复制或下载
- 不自动发送。没有任何网络请求（`CLAUDE.md` R8）
- 报告顶部写明：本文件不含任何金额、姓名或账号信息
- 有一个自动化测试：对所有 golden case 生成报告，grep 断言不含数字模式（除白名单字段）

## 5. 反馈如何转化成 golden case

同事报告了一个失败，你**不能**拿他的文档去复现。流程是：

1. 从自检报告拿到失败路径 ID、券商、校验编号、差额数量级
2. 找他补一份 §3.1 的结构描述（如果是版式问题）
3. **用合成方式重建这个场景**，加入 golden set
4. 修复后让他重新跑一遍，看自检报告是否转绿

第 3 步是关键：**每个真实反馈最终都变成一个合成 golden case。** 这比直接拿他的文档做 case 更好——合成 case 可以进仓库、可以进 CI、可以永久保留，而真实文档三者都不行。

## 6. 三层测试

### 6.1 Property test（`test/property/`）

`fast-check` 生成随机但合法的 lot / sale 组合，验证 `docs/02` §4 的 7 条不变量。生成器覆盖：分数股、同日多 vest、跨 lot 卖出、单 lot 多次卖出、零卖出、全部卖出。

测的是逻辑正确性，不依赖真实文档。每次提交都跑。

### 6.2 Golden test（`test/golden/`）

全量比对，金额零容差（到分），股数零容差。失败时输出 diff 表：case_id / 字段 / 期望 / 实际 / 差额。

### 6.3 确定性 test

每个 golden 文件解析两次、计算两次、生成 xlsx 两次，三层各自 diff 必须为空。

---

## 7. 答案怎么来

按可信度排序：

1. **合成构造** — 答案由构造过程直接给出，天然正确。内部阶段的主力
2. **手算** — 用纸和计算器完整走一遍，每组 1–2 小时。至少 3 组
3. **交叉工具比对** — 不可作为唯一来源，它也可能错

**禁止用本工具自己的输出作为期望值。** 这是最容易犯的错：跑一遍、看着挺对、存成 expected。这样测试只能锁住「行为没变」，锁不住「行为是对的」。

---

## 8. 阶段验收门槛

| Phase | 门槛 |
|---|---|
| P1 | 7 条 property 全过；golden 100% 匹配（手工喂 schema，不测提取） |
| P2 | 提取准确率 ≥ 99.5%；**静默错误率 = 0**；确定性 test 全过 |
| P3 | xlsx 自检全过；三平台打开无公式错误 |
| P4 | 自检报告不含数值（自动断言）；构建产物零网络请求 |
| P5 | 连续 20 次运行无 `InvariantViolation`；所有报告过的失败可用合成 case 复现 |

### 关于「静默错误率 = 0」

P2 唯一不可妥协的指标。

提取率 99.5% 意味着每 200 个字段错 1 个，这**可以接受**——只要那 1 个会被 C1（合计锚定）或 C2（乘积一致）捕获并阻断。不可接受的是错误既没被捕获、又流进了最终的 xlsx。

衡量方式：在 golden set 上人为注入单字段扰动（改一位数字、串行、漏一行），验证每种扰动都被至少一条校验捕获。**捕获率必须是 100%**，且这个注入测试要自动化。

---

## 9. 回归纪律

- 每次涉及计算或解析的改动，改前跑基线并记录
- golden 上任何一格变化都必须能解释；不能解释就是回归
- **不允许通过修改 expected 来让测试变绿**，除非能独立手工验证新答案，并在 commit message 里写出手算过程
- 新增 golden case 时先跑一遍看是否已经通过；如果直接就过了，说明没增加覆盖，换一个更难的

两个 case 的期望值都用独立脚本验算过 I1–I6、proceeds 分摊、持有期、8949 每行的调整额与损益、以及各级合计。

验算脚本落在 `test/golden/verify.py`，**不依赖被测代码**——这是它的全部意义。构造新 case 后必须运行，CI 里也跑一遍。

```
python3 test/golden/verify.py
```

它验的是：I1、I2、I4、I6 精确等式、proceeds 分摊、加法式 basis 定义、持有期边界、8949 两种输出形态、各级合计。

**不要靠肉眼核对。** `synthetic-002` 最初的期望值就是靠这个脚本才发现写错的——往年 vest 的 lot，其代扣卖出不在本年 1099-B 上，导致「未匹配股数」被误标成「仍持有」。这个区分后来写进了 `docs/02` §3.1。
